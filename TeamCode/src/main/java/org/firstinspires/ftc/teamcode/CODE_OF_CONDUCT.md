# Team BioBuzz (37261) - Code of Conduct

## Overview
This document outlines the expectations for all members of Team BioBuzz regarding our technical work and collaboration. Our primary goal is to foster a learning environment where every student gains a deep understanding of the technology behind our robot.

---

## 1. Technical Integrity & AI Policy
In this team, our goal is learning and mastery. While AI tools (like ChatGPT, GitHub Copilot, or Gemini) can be powerful assistants, they must be used responsibly to ensure every student understands the robot they are building.

### 1.1 The "Explainability" Rule
*   **The Standard:** You are responsible for every line of code you commit. You must be able to explain the logic, syntax, and purpose of any code added to the repository.
*   **Verification:** During code reviews, mentors or peers may ask you to explain a specific block. If you cannot explain how it works, the code will not be merged until you have researched and understood it.

### 1.2 Using AI Tools
*   **Prompt for Learning, Not Just Code:** Use AI to understand concepts, not just to generate snippets. Instead of asking an AI to "write a drive script," ask it to "explain how a PID loop works in Kotlin" or "help me debug why my motor isn't stopping at a specific encoder count."
*   **Attribute Your Assistant:** If a significant block of logic was generated or heavily inspired by AI, include a comment at the top of the function or class. 
    *   *Example:* `// PID logic structure generated by AI; tuned and adapted by [Student Name] for 40:1 motors.`
*   **Verify Before Committing:** AI-generated code often misses FTC-specific nuances (like hardware lifecycles or motor directions). Never commit AI code without testing it on the robot first.

---

## 2. Version Control (Git) Policy
We use Git not just to save code, but to tell the story of our engineering journey. This is a critical part of the Engineering Notebook.

### 2.1 Commit Standards
*   **Atomic Commits:** Keep commits small and focused on a single change (e.g., "Add deadzone to joysticks" rather than "Updated everything").
*   **Descriptive Messages:** Use clear, action-oriented commit messages. Avoid vague messages like "fix" or "code."
*   **Transparency:** Avoid large "mega-commits" where hundreds of lines appear at once. This usually indicates a blind copy-paste and bypasses the learning process.

### 2.2 The Pull Request (PR) Workflow
*   **Peer Review:** No code is merged into the main branch without a peer or mentor review.
*   **Demonstration:** Before merging, the author should be prepared to demonstrate the code's functionality on the robot (or a simulation).
*   **History is Documentation:** Remember that judges may look at our GitHub history to see how we solved problems. A history of thoughtful, incremental changes is much more impressive than a series of large, unexplained blocks.
